# PRODUCT · OpenSpec read compatibility

Baseline [Engine I1](../../../product/features.md); add an explicitly namespaced, local, noninteractive compatibility reader for an existing OpenSpec specification. This increment implements the narrow forms below, preserving the remaining [full OpenSpec/factory roadmap](../2026-11-26_engine-foundation/process.md). It does not certify all OpenSpec behavior, migration, validation or other commands.

## Supported interface and constraints

- `pentapro compat openspec list --specs [--json]`
- `pentapro compat openspec show ID --type spec [--json]`

Option ordering is flexible within the compatibility command. No implicit native `--root` selection, interactive prompts, filters, stores, worksets, `--no-interactive`, aliases or color options in this increment. `--json` is local to each compatibility command; global native `--root`/`--json` cannot be mixed in. All missing/extra/unknown arguments and `compat openspec validate` fail with exit 2, no stdout, a human diagnostic on stderr explicitly identifying unsupported syntax/command; `--help` describes only implemented forms. This explicit unsupported diagnostic is an intentional incremental divergence, not OpenSpec parity. CLI syntax failure occurs before any project read/write. Do not imply unsupported options succeeded.

### Resolution and scope

The following are deliberate, temporary restrictions until the complete pinned resolver is ported; refusal never claims the upstream command would also refuse. Before every supported command, read-only preflight must reject with stderr `unsupported root selection\n`, empty stdout and exit 2 if: a project candidate on the ancestor walk contains `openspec/config.yml`, an `openspec/config.yaml` other than the exact UTF-8 bytes `schema: spec-driven\n`, any existing `.openspec-store` entry under either `openspec/specs` or `openspec/changes` (a conservative superset of upstream’s `.openspec-store/store.yaml` marker), a symlinked or nonregular root/config/marker, an inaccessible or uninspectable candidate, an existing OpenSpec global config directory `$XDG_CONFIG_HOME/openspec` (fallback `$HOME/.config/openspec`), or an existing OpenSpec global data directory `$XDG_DATA_HOME/openspec` (fallback `$HOME/.local/share/openspec`). For each XDG variable separately, **unset** selects its HOME fallback; if set, the value must be nonempty, absolute, valid Unicode and an inspectable path, otherwise refuse. HOME is required only for a selected fallback and must likewise be nonempty, absolute, valid Unicode and inspectable. A missing resulting `openspec` child is allowed; an existing file, directory, symlink or other object at that child refuses. Distinguish missing (ENOENT) from inaccessible or other metadata errors; the latter refuse. This conservative Linux-only policy rejects even benign global configuration and ignored store pointers; it preserves them and is a documented incremental divergence. Read-only existence/metadata checks must neither create these paths nor read/display credentials. Explicit `--store` and native `--root` are already unsupported. On other operating systems fail unsupported until platform-specific global path resolution is reviewed.

Evaluate syntax first, then effective global config/data paths, then inspect ancestors from CWD upward. At each ancestor inspect `openspec`, config names and the two planning directories plus marker entries before deciding qualification; stop at the first qualifying root and do not inspect ancestor project candidates above it. Global path preflight applies even when the nearest root would win upstream (documented conservative divergence). `ENOENT` of a candidate or optional marker means absent; `EACCES`, non-directory components, symlinks or other metadata failures during that preflight produce `unsupported root selection` exit 2. In particular, a mode-000 `openspec/specs` directory makes metadata inspection of `specs/.openspec-store` fail with EACCES under nonroot Linux: preflight therefore returns `unsupported root selection\n` on stderr, empty stdout, exit 2, even though upstream returned a scan error for that fixture. This is an intentional conservative divergence. Only if every metadata preflight succeeds and a later directory enumeration returns EACCES does the JSON/human scan error below apply. An execute-only directory exercised that distinction in the [mode-0111 follow-up](../../../../docs/agents/runs/engine-openspec-read/eacces-followup.md) on Linux. Walk from current directory upward and consider a qualifying nearest local root only when its regular `openspec/` contains a regular `specs/` or `changes/` directory (with no store metadata marker) or an accepted exact `config.yaml`; a bare empty `openspec/` is not a root. A legacy `openspec/project.md` with no other qualifying shape is outside I2 and receives `unsupported root selection` exit 2, even though upstream list may choose implicit root. If no qualifying root or override exists, `list --specs --json` returns the pinned [no-root JSON](oracle-boundaries.md#no-project), and human list emits the literal Unicode cross and Fix lines on stderr in [no-root-human-list](oracle-readiness.md#no-root-human-list), exit 1. In the same context typed `show alpha --type spec` uses implicit current directory as upstream, emitting the missing-spec diagnostic on stderr in human mode or `show_error` JSON on stdout in JSON mode, exit 1; no root field. Do not assume show emits list's `no_openspec_root`. The chosen nearest root returns absolute path and source `nearest`, including nested CWD. Walk past a bare nonqualifying `openspec/` and continue to a qualifying ancestor. Inability to inspect any ancestor or the effective global paths is unsupported, never silently treated as missing. Linux Node 26.10 reproduced 33 cases and a nonroot specs-directory EACCES case; Node 24, other permission cases and other OS semantics remain unverified.

### Lists (I2-001)

Given `<root>/openspec/specs`, find nested `<id>/spec.md` entries; ignore dot directories, symlinked directory traversal and `specs/spec.md` at the root; treat a missing specs directory as empty. Preserve pinned traversal, contained spec-file link, dangling link and external link behavior below. IDs are `/`-separated relative paths. Parse each spec for `requirementCount`; read/parse failure for an otherwise discovered entry yields count 0 as in `src/core/list.ts`, not global failure. JSON stdout has `specs` array of `{id, requirementCount}` and `root` `{path: ABSOLUTE, source: "nearest"}`, 2-space indentation and final newline. Text stdout is `No specs found.\n` for empty or `Specs:\n` then two spaces + padded id + five spaces + `requirements N\n`, widths and order as the upstream Node runtime. JavaScript localeCompare differs from byte ordering even for mixed-case and punctuation ASCII IDs; see [ordering observations](oracle-readiness.md#order-c). This increment supports listed IDs only when each path segment matches `[a-z]+` and either all IDs are single-segment or the result contains exactly one nested ID and no other IDs. Any other ID set, including multiple nested IDs, mixed nested/single IDs, digits, uppercase, punctuation, non-ASCII or non-UTF-8 IDs, fails before emitting a success result with stderr `unsupported spec identifier ordering\n`, empty stdout and exit 2. For an accepted multi-ID single-segment set use alphabetical ascending order; test representative prefix pairs against pinned Node. This is a conservative incremental divergence, not general locale parity. A single nested ID may be shown/listed; support for the prior alpha plus platform/session multi-ID fixture is deferred. An external spec-file symlink causes the entire JSON list to return `{"specs":[],"root":null,"status":[{"severity":"error","code":"list_error","message":...}]}` on stdout and exit 1, even when another entry is valid; exact message/path semantics follow the [boundary evidence](oracle-boundaries.md#symlink-list). Only after successful preflight, on nonroot Linux, if enumeration of `openspec/specs` fails with EACCES, JSON stdout is `{ "specs": [], "root": null, "status": [{ "severity": "error", "code": "list_error", "message": "EACCES: permission denied, scandir 'ABSOLUTE_SPECS_PATH'" }] }`, pretty-printed with final newline; exit 1, empty stderr, as the upstream diagnostic shape [observed under effective UID 1000](oracle-stable-node.md#inaccessible-specs-directory); the observed mode-000 case itself fails earlier in Engine preflight, and the post-preflight scan branch was observed for mode 0111 in the [follow-up](../../../../docs/agents/runs/engine-openspec-read/eacces-followup.md). For human mode, render the same diagnostic message as `✖ Error: {message}\n` on stderr with empty stdout and exit 1; append `Fix: {fix}\n` only when that diagnostic supplies a fix. This is the pinned noninteractive Linux `ora().fail` renderer with NO_COLOR, established no-root fixture and source; the EACCES and link human forms require differential controls. For an OS error whose platform/code-to-Node message mapping has not been implemented and tested, fail instead with `unsupported filesystem error\n` on stderr, empty stdout and exit 2: this is an explicit temporary divergence, never a successful empty list. List success is exit 0, stderr empty.

### Show (I2-002)

For normal success, ID is one or more `/`-separated segments each matching `[a-z]+`. Nonmatching IDs fail with stderr `unsupported spec identifier\n`, empty stdout and exit 2, except the explicit traversal security scenario below. Reject absolute IDs and lexical traversal such as `../alpha`; where upstream emits its `show_error` JSON with exit 1, match the observed JSON output and absolute path message, including `../alpha` from [oracle](oracle-observations.md). These lexical ID checks do not imply that all physical reads remain inside the selected project: the explicitly selected directory-symlink case below is a deliberate compatibility boundary. On text mode, raw Node UTF-8 decoding replaces invalid bytes with U+FFFD; print decoded content exactly with one additional LF, preserving BOM and original CRLF in the decoded content. On JSON mode, parse using pinned Markdown semantics below and emit keys in this order with 2-space indentation and trailing LF: `id`, `title` (the supplied ID), `overview`, `requirementCount`, `requirements`, `metadata` `{version:"1.0.0",format:"openspec"}`, `root`. Requirement entries are `{name,text,scenarios}`; scenario entries `{name,rawText}`. See [observed output](oracle-observations.md#openspec-show-alpha---type-spec---json-project) for the exact simple example. Successful output exit 0, stderr empty.

For a missing typed spec, JSON stdout is `{ "status": [{ "severity":"error", "code":"show_error", "message":"Spec 'ID' not found at ABSOLUTE_PATH" }] }` with 2-space indentation and final LF; exit 1, empty stderr. Missing Purpose or Requirements, dangling spec-file links, external traversal and tree-wide discovery errors follow pinned `show_error` envelope/message as observed in [boundaries](oracle-boundaries.md). Only if preflight succeeds and a later specs-directory scan returns EACCES, typed JSON show emits `{ "status": [{ "severity": "error", "code": "show_error", "message": "EACCES: permission denied, scandir 'ABSOLUTE_SPECS_PATH'" }] }` with final newline, exit 1 and empty stderr; see [upstream stable-node evidence](oracle-stable-node.md#inaccessible-specs-directory); the tested mode-000 case is refused earlier by Engine and the post-preflight scan branch was observed for mode 0111 in the [follow-up](../../../../docs/agents/runs/engine-openspec-read/eacces-followup.md). In human mode render supported operational diagnostics as `✖ Error: {message}\n` on stderr with empty stdout and exit 1, optionally followed by `Fix: {fix}\n` when present, matching the pinned noninteractive Linux `ora().fail` route. Unknown/unmapped filesystem errors instead receive `unsupported filesystem error\n` on stderr, empty stdout and exit 2 as an explicit temporary divergence. Differential controls must cover missing spec and external link human forms before acceptance. Separately assert the Engine-only mode-000 preflight refusal; compare post-preflight scan EACCES human forms against the mode-0111 follow-up. Do not label mode-000 Engine behavior equivalent to upstream. No error may silently return unrelated data or exit 0. Discovery checks happen before a typed show: an external spec-file link elsewhere can cause show of an otherwise unrelated valid ID to fail, as observed. Internal contained spec-file links and explicitly shown directory links work as observed; dangling links fail for explicit show; directory links are not listed.

**I2-005 — Explicit directory-symlink trust boundary.** A supported lexical ID can select a capability directory that is a symbolic link to a directory outside the selected project. For `show ID --type spec` (human or JSON), the pinned OpenSpec treats that capability directory as its own trust root; when the final `spec.md` resolves within that directory, the command can read and output external content accessible to the invoking process. This is deliberate compatibility with the [independent verification fixture](../../../../docs/agents/runs/engine-openspec-read/verification-first.md) and pinned `src/utils/spec-path-containment.ts` (`assertDiscoveredSpecFile`), not a guarantee of containment within the project. Discovery for `list --specs` does not traverse directory symlinks, so the linked capability is absent from the list. A `spec.md` file symlink discovered under a real project directory must resolve within the project; an external target fails the whole discovery as in I2-001. For an explicitly selected linked capability directory, permit the final file if its canonical target remains within that capability directory. If the final `spec.md` is itself a symlink to a target elsewhere within the project, the project-file fallback is permitted only when the canonical directory holding that file link is within the canonical specs root; it is not an unconditional project-target exception. Thus, if `<project>/openspec/specs/alpha` links to an outside directory and that directory’s `spec.md` links back to `<project>/docs/spec.md`, reject the composed path: the fallback parent is outside the specs root. Match pinned OpenSpec’s exit 1 and `show_error` diagnostic naming `<project>/openspec/specs/alpha` in JSON, and its human error renderer in text mode. A file link resolving outside both the capability directory and project is rejected. A dangling file link fails as specified above. Absolute and `..` IDs do not receive the capability-directory exception. The external directory target's files and names are not a grant to write: I2 remains read-only and cannot perform migration or arbitrary writes.

A project controlled by an untrusted party can direct an explicit `show` read to an external directory readable by the invoking user and expose its `spec.md` contents in stdout or downstream agent context. Use only trusted projects/capability links or isolate the process with host filesystem permissions when that disclosure matters. The Engine does not provide a sandbox or promise physical project-root containment. Static link checks also do not establish race-free behavior against concurrent path replacement. This compatibility choice follows the user's requested OpenSpec behavior and applies only to this I2 reader; it does not waive separate host authorization or other Engine boundaries.

### Markdown contract

The oracle is pinned source `src/core/parsers/markdown-parser.ts`, `requirement-text.ts`, `requirement-blocks.ts` at `f1cd852f4edce22b8df9548a4df889172ca8ff25` and its tests, not a generic Markdown parser. Parse spec JSON as upstream: decode UTF-8 with replacement, strip one leading BOM for parsing, normalize CRLF and CR to LF, ignore fenced lines when detecting headers, detect levels 1–6 and closing heading marks, build hierarchy and find first case-insensitive Purpose/Requirements section. Missing/empty Purpose produces `Spec must have a Purpose section`; missing Requirements produces `Spec must have a Requirements section`. Every direct child of Requirements becomes a requirement, with name normalization, shared fenced/metadata-aware requirement text extraction and fallback; child scenarios with a meaningful body become scenarios. Exact trimming, fence masks, metadata and name rules are the pinned helpers' behavior and must be ported/tested before claiming broad support; a simplistic header counter is insufficient. Text show does not parse Markdown. Implement the complete pinned `parseSpec`, `parseSections`, `findSection`, `parseRequirements`, `parseScenarios` and invoked `requirement-text.ts`/`requirement-blocks.ts` helpers, including code-fence masks and name/body semantics; these finite source routines are the normative contract for all decoded input. There is no catch-all unsupported lexical class in this increment: an implementation unable to handle a construct blocks acceptance rather than guessing or selectively refusing it. Upstream parseSpec missing/empty Purpose and missing Requirements are parser errors; list catches these and file read errors per entry and emits `requirementCount: 0`, whereas JSON show emits `show_error` exit 1. Raw text show bypasses parseSpec. Directory discovery errors, including unsafe external symlinks, are whole-command errors and never downgraded to zero. This precedence is mandatory and must be tested with the same malformed spec in list and show.

## S1–S7 acceptance journeys

S1: list a same-depth set of simple lowercase IDs and separately one nested platform/session ID from project/nested CWD; root.path is actual absolute root, source nearest, matching stdout/exit/stderr. Mixed or more complex ID sets refuse explicitly. S2: show supported single and nested IDs in separate admissible projects in text and JSON; text bytes preserve input plus LF, JSON reflects sections/scenarios. S3: empty/missing project, missing typed ID, traversal and malformed/no-purpose cases reproduce captured exact diagnostics, including path replacement only in comparison harness. S4: BOM/CRLF/fenced fake heading and invalid UTF-8 match oracle. S5 / I2-005: compare internal and external spec-file links, dangling links, and explicit internal and external capability-directory links; external directory show returns the sentinel content, an external directory whose final file links back into project/docs is rejected with the capability-directory diagnostic, directory links are absent from list, lexical traversal is rejected, and an external spec-file link can fail discovery for unrelated show. S6: unsupported command/options, incompatible root selection and unmapped OS errors fail explicitly; no implicit fallback. Parsing follows the complete pinned helper path, not an undefined unsupported-construct classifier. S7: compare project, isolated HOME and relevant config before/after each real process; observe no persistent mutations; also inspect operation code for network/process/writes. A byte snapshot cannot prove absence of transient writes. Native I1 journeys remain passing.
