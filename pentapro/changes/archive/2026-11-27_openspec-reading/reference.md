# I2 compatibility research: a first real OpenSpec spec journey

Source-only investigation, 2026-11-26; upstream OpenSpec v2.2.0 SHA f1cd852f4edce22b8df9548a4df889172ca8ff25. No upstream CLI or tests executed; local clone lacks installed node_modules/dist. The existing `openspec-inventory.md` remains the broader source map. A differential executable oracle is a prerequisite to claiming equivalence, not a result of this report.

## Recommended bounded journey

An engineer has an existing local OpenSpec project and asks an agent to discover, inspect and validate a single capability without modifying any file. Add explicitly namespaced commands, e.g. `pentapro compat openspec list --specs --json`, `pentapro compat openspec show alpha --type spec --json`, and `pentapro compat openspec validate alpha --type spec --json`. Support also text variants, `--no-interactive`, and nested current-working-directory root discovery. No native `pentapro/` schema or content is implicitly migrated. Preserve all other OpenSpec flags in the complete product roadmap: do not accept unsupported flags and silently ignore them. This slice is a stepping stone, not feature-family parity.

Fixture under a temporary project root:

```text
openspec/config.yaml
openspec/specs/alpha/spec.md
openspec/changes/
```

Populate `config.yaml` with an upstream-valid schema declaration verified against the oracle; adopt `test/commands/validate.test.ts` source fixture (Purpose text sufficiently long; one `### Requirement`, normative SHALL body, one `#### Scenario` with GIVEN/WHEN/THEN). Also add `specs/platform/session/spec.md` for nested IDs, a `.hidden` directory, and an extra `specs/spec.md` at root. Snapshot bytes before/after all commands. `--type spec` avoids auto-resolution ambiguity initially; test ambiguity explicitly before advertising automatic inference.

## Observed contract to implement against pinned source

- Top-level registrations/flags: `src/cli/index.ts:470–510`, `643–684`. `list --specs` delegates to ListCommand; `--archived`/`--all` with specs produces error `--archived and --all can only be used when listing changes.` Current list `--sort` is only applied to changes; spec ids sort via localeCompare in `src/core/list.ts:245–299` (discovery itself initially code-point sorts). Do not assume Unicode ordering equivalent to Rust byte sorting without fixtures/declared locale policy.
- List JSON stdout is `{ "specs": [{ "id": "alpha", "requirementCount": 1 }, ...], "root": { "path": ABSOLUTE_PROJECT_ROOT, "source": ROOT_SOURCE } }`, pretty printed; no specs is an empty array, exit 0. Raw `ListCommand` unit tests may omit root, but the real top-level command attaches it. `root.source` is resolved by `src/core/root-selection.ts`, not hard-coded. On parser/read errors list includes the discovered item with count 0, not a global error. Human mode prints `Specs:` and aligned `requirements N`, or `No specs found.`. Discovery recursively finds `<id>/spec.md`, skips dot directories and symlinked dirs, ignores root `specs/spec.md`, and checks `spec.md` symlink containment; dangling links ignored (`src/utils/spec-discovery.ts`, `src/utils/spec-path-containment.ts`). Malformed/unreadable tree handling differs: ENOENT => empty; other readdir errors propagate. `list` `fs.access` failure has its own empty fallback; test rather than infer all access semantics.
- `show alpha --type spec` text is raw UTF-8 spec markdown passed through `console.log`, which adds one newline, even when file already ends in newline (`src/commands/spec.ts`). JSON is `{ id, title, overview, requirementCount, requirements, metadata, root }`. `title` is the supplied spec id, **not** first Markdown title. `metadata` defaults to `{ "version":"1.0.0", "format":"openspec" }`; each requirement contains `{name,text,scenarios}` and scenarios `{name,rawText}`. `--requirements` or `--no-scenarios` makes `scenarios: []`; `-r, --requirement <id>` is 1-based, using JavaScript `parseInt` behavior in source, and reduces output/count. Conflicting `--requirements`+`--requirement` errors; fixture the precise top-level catch/stdout/stderr. Parse canonical `Purpose` and `Requirements`, BOM, CRLF, fences, closing heading markers, hierarchy, scenario content via `src/core/parsers/markdown-parser.ts`, `requirement-text.ts`, `requirement-blocks.ts`; do not implement only simple regexes and claim semantic parity.
- `validate alpha --type spec --json` output is `{ "items":[{"id":"alpha","type":"spec","valid":true,"issues":[],"durationMs":NUMBER}],"summary":{"totals":{"items":1,"passed":1,"failed":0},"byType":{"spec":{"items":1,"passed":1,"failed":0}}},"version":"1.0","root":{...} }`; valid exit 0, invalid exit 1; JSON goes stdout. `durationMs` is observed elapsed wall-clock, nondeterministic; differential tests validate type/range and normalize only this field and temp paths. Issue objects use `level` (`ERROR`, `WARNING`, `INFO`), `path`, `message`; warning/strict validity semantics are in `src/core/validation/validator.ts` and schemas, not simply nonempty required files. `validate` diagnoses unparseable config before validating (`src/commands/validate.ts:106–141`). The initial implementation must either port complete spec validation behavior with tests or explicitly report unsupported input; it must not claim successful validation on an unimplemented rule. `--strict`, bulk and findings are separate surfaces unless fully ported.
- Unknown or ambiguous direct item in auto-detect JSON emits `{ "status":[{"severity":"error","code":"unknown_item"|"ambiguous_item","message":...,"fix":...optional}] }` to stdout, exit 1 (`src/commands/show.ts:105–180`, `src/commands/validate.ts:240–296`); type override skips membership check and may instead generate file error/report. Root-selection failures and errors use `src/core/root-selection.ts` and `src/commands/shared-output.ts` contracts, not native Engine schema/errors. Missing-name noninteractive hints can be stderr prose even with JSON, per source; verify with real oracle before asserting.

## Evidence & negative checks required

1. Execute pinned upstream CLI and Rust binary on identical safe fixture copies with same cwd/environment; compare stdout JSON semantically and stdout/stderr+status for text, matching all keys/omissions. Normalize root path and validation duration only with explicit justification. Preserve upstream license/attribution if reusing test text. `NODE_OPTIONS`, telemetry/update network suppression, HOME and config isolate test runner; inspect effects before invoking. Pin node/dependencies; don't download arbitrary latest packages.
2. Full journey: list flat/nested, show raw/JSON/filtered, validate valid, edit controlled fixture to invalid, validate diagnostic/nonzero, repair and pass; snapshot all non-test files to prove read-only. Include empty/no-root/missing name, type ambiguity, missing files and malformed config.
3. Hostile/boundary fixtures: markdown fences, title closing hashes, CRLF/BOM, empty scenario, non-normative requirement, missing purpose/requirements, nested ID, invalid traversal, symlinks in/out, dangling symlink and read errors, strict warnings. Tests verify no accidental writes even for errors.
4. `durationMs`, platform path output, case/locale, TTY and inaccessible filesystem differ by environment; isolate, compare and report. Scope/OS limitations explicitly; no invented all-platform parity.
5. Begin contract with an atomic support matrix, exact fixture results and source pointers. If upstream unavailable, source inspection plus authored expectations is weaker than differential execution and cannot satisfy a differential gate. Consider a smaller slice list + show with validate held explicitly unsupported if complete validator cannot be implemented safely in one reviewed increment; tell user validation is not yet compatible rather than emit a false success.
