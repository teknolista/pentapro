# Coordinate a software factory run

Deliver the user's requested outcome, not merely a plan. Apply project instructions and use existing specialist skills as owners; this skill coordinates their handoffs and does not replace them. When project-local factory roles are available, use the applicable `factory_spec`, `factory_implementer`, `factory_verifier`, `factory_reviewer`, `factory_retrospective` and `factory_shipper` roles for delegated work; the main agent orchestrates and integrates. Resolve logical role names to the host-discovered IDs before invocation; Cursor profiles use hyphenated names and OpenCode profiles use filename stems such as `factory-shipper`. Check actual host availability and policy. Maintain a compact run ledger and continue between completed stages without asking again for authority already granted. Read [the execution contract](references/execution.md), [role packets](references/roles.md), and [retrospective protocol](references/retrospective.md).

1. **Intake and baseline.** Identify repository, current work, request, target, branch and project policies, applicable skills, and separately authorized operations. Preserve existing work. Check only relevant safe prerequisites and baseline checks; record failures and unavailable targets. Choose a proportionate path: Record inapplicable optional stages with their reasons. Keep required gates pending until satisfied or lawfully waived under the project policy. Record unavailable verification explicitly.
2. **Specify and review.** For an OpenSpec request use the applicable explore/propose or apply skill; use PentaPRO when the project requires it. Review scope, canonical rules, risks, observable acceptance criteria, negative cases and feasible checks. Resolve routine choices; escalate only consequential ambiguity. A requested specification-only task stops there; an implementation request authorizes the necessary specification work and subsequent implementation.
3. **Plan and implement.** Split into small verifiable vertical slices with dependencies, paths, acceptance checks and evidence. Delegate independent tasks with disjoint write ownership when available. Execute the authorized work rather than stopping after investigation. Apply domain skills and project instructions; reconcile material contract conflicts before dependent edits.
4. **Verify and independently review.** Run appropriate checks on the integrated snapshot, exercise relevant real entry points, and map criteria to results or explicit gaps. Request a fresh read-only reviewer when available and authorized. Treat review as a separate judgment, not a test result. Substantiate findings, implement authorized fixes, rerun affected checks and re-review the changed snapshot. Keep retries bounded; report specific unresolved blockers. A self-review is not independent.
5. **Reconcile and deliver.** Update affected canonical specifications, tasks, documentation and evidence; verify final snapshot and rerun checks affected by reconciliation. Use git-ship or the applicable Git skill for explicitly authorized commit, push or PR. Verify actual published revision and CI where available. Merge, release, deploy and OpenSpec archive each require applicable authority. If archive follows publication, account for archive changes: validate and publish the resulting archive revision if authorized; otherwise report it as local pending publication. Never report the earlier revision as containing the archive.
6. **Retrospect.** After the requested terminal stages, independently assess the run using the retrospective protocol. If a requested stage cannot be completed, capture a provisional retrospective with that gap and resume when resolved. Propose improvements with evidence and expected effect; do not silently alter reusable skills or claim measured savings without a comparison.

For factory runs and substantial dependent multi-agent work, maintain a durable execution record following [run persistence](references/run-records.md) before delegation and at handoff, external-effect and recovery boundaries. Default to `docs/agents/runs/<run-id>/run.json`, or reuse an approved equivalent. Only the orchestrator writes it. If persistence is prohibited or unavailable, report the recovery gap; a conversational handoff is not durable recovery evidence. Ordinary bounded single-agent edits remain proportionate. Never put secrets or raw personal information in run records. Respect user permissions, sandbox and host restrictions; instructions and delegated packets do not grant tool permissions. If delegation is unavailable, do the available work directly, disclose lost independence, and leave any mandatory independent-review gate incomplete.

## Continuous improvement for every role

Use a proportionate PDSA cycle for each role: plan the contextual task and checks, execute through the owning skills, study observed results, and make authorized corrections with affected rechecks. Include this contract in every role packet, even for standalone work. Read the project-installed `docs/agents/continuous-improvement.md` (or approved equivalent) and relevant lessons; when absent, use this short cycle and report the setup gap. Bound repeated corrections to two attempts for the same failure, stopping sooner without progress; preserve read-only boundaries and route fixes to their authorized owner.

Collect outcome, checks/gaps, PDSA summary and useful lesson candidates (context, evidence/snapshot, cause confidence, correction/result, proposed prevention, limits and next check). `No new lesson identified` is valid. The orchestrator alone serializes and deduplicates writes to `docs/agents/lessons-learned.md` or the existing approved record, preserves previous entries, distinguishes hypotheses from validated local results and rereads saved entries before reporting persistence. Write every persisted lesson entry in English, including its title and all fields, even when project specifications or conversations use another language. Translate and summarize relevant observations into English; retain technical identifiers and source quotes only when needed, with an English explanation. This applies to the project's lessons record in `docs/` or its approved equivalent and keeps lessons reusable for improving the PentaPRO skills. Without a recording owner or write access, return the candidates and mark persistence pending. For isolated agent calls, the invoking main session is the orchestrator; direct main-agent selection must separate role execution from recording. Late lessons can remain local for the next authorized commit; do not create additional publication merely to include them. Reusable instruction changes require their own authority and evaluation.
