# Coordinate native PentaPRO delivery

The host's main session is the principal exploration/orchestration agent. A developer describes the outcome once; guide clarification, delegate to the installed specialist roles, integrate checked results and continue all authorized stages without requiring a prompt for each skill. Respect the user's selected scope, configured role models/effort, permissions and explicit stopping points. Read [the lifecycle](references/execution.md) and [role packets](references/roles.md). PentaPRO owns specification content, Software Delivery owns task execution and this skill owns change lifecycle and orchestration. Companions are optional: use the project contract directly when unavailable and report any missing required expertise or independence.

## Standard loop

1. **Explore and establish scope.** Read project instructions, current source, maintained pillars, active changes and relevant lessons. Infer routine choices; ask for consequential missing decisions. An exploration/specification-only request does not authorize implementation. A request to develop an outcome includes necessary specification and implementation; apply the normal final acceptance gate unless explicitly changed by the developer.
2. **Open or resume one change.** Use `pentapro/changes/<name>/`, two or three lowercase words separated by hyphens. Inspect active and archived names and never reuse an existing identity or overwrite a destination. Use the fixed [artifact contract](references/change-records.md); no configurable schema, special command or SDD CLI is needed. Resolve the actual project root and symlinks before writes. Do not mistake archive or README indexes for active changes.
3. **Specify before dependent implementation.** With penta-pro, author `change.md` and all five dimension files inside the active change. Identify the baseline revision and affected IDs. Greenfield root pillar scaffolds remain Pending; brownfield baseline remains authoritative until accepted consolidation. Clarify compatibility and acceptance scenarios. Dispatch `factory_spec` on the saved contract; resolve findings and rereview affected decisions. Record the reviewed contract snapshot. The reviewer never authors its own acceptance.
4. **Plan and build.** Use software-delivery; `process.md` owns numbered checkbox tasks, dependencies, paths and verification per increment. Delegate bounded slices to `factory_implementer` and relevant implementation/testing skills. Preserve unrelated work; disjoint files are required for concurrent writes. Record actual results and interrupted work as it happens. A changed contract invalidates affected specification review and checks.
5. **Verify, review and correct.** Dispatch `factory_verifier` for criterion-to-evidence assessment and a fresh `factory_reviewer` for implementation defects on the fixed integrated snapshot. Test real relevant entry points and negative cases. Route fixes to the implementer, rerun affected checks and rereview. Use bounded corrective attempts and investigate non-progress; do not run an infinite loop or equate document/task completion with working software.
6. **Request developer acceptance once.** When required checks/reviews pass, set Awaiting acceptance and present changed behavior, evidence, limitations and pending closure effects. Wait for explicit result approval. By default that single approval authorizes consolidation, archive, commit and normal push for this change; tell the developer this scope when presenting the result. Approval of the process design, silence, elapsed time and a model verdict are not result acceptance. Honor explicit separate, local-only, review-only or no-publication instructions. Negative feedback returns to clarification/design and affected implementation/review; preserve the previous baseline and invalidate stale evidence.
7. **Close the accepted change.** Follow [consolidation and archive](references/closure.md). Use penta-pro to reconcile all affected baseline pillar records, preserving unrelated requirements/scenarios and IDs. Recheck the reconciled snapshot. Only then move the active directory to `pentapro/changes/archive/YYYY-MM-DD_<name>/` using the developer's local date and repair incoming/outgoing links. Archive date, disposition, implementation, validation and publication remain separate facts.
8. **Publish and retrospect.** For default accepted delivery, delegate git-ship work to `factory_shipper` when available with its configured settings. Verify exact reviewed commit and remote ref and applicable CI. Explicit narrower authority prevails; merge, deploy, release, force push and history rewriting require their own authority. Publication failure preserves the local commit/archive and records what is uncertain; inspect effects before retrying. Run [retrospective](references/retrospective.md) after requested terminal stages, or label it provisional when a stage is blocked. Return outcome and saved versus unpublished records honestly.

For cancellation, interruption, conflicting changes and resumption use [closure and recovery](references/closure.md). Cancelled intent is never consolidated as delivered behavior. Preserve and reconcile any retained partial implementation and required recovery before archival; no automatic source rollback.

Maintain one durable execution record for substantial runs following [run persistence](references/run-records.md), before delegation and at external-effect/recovery boundaries. Only the orchestrator writes it. Use an approved project equivalent or the existing optional record helper; it is bookkeeping, not an SDD coordinator or proof of evidence truth. If persistence is unavailable report the recovery gap. Host permissions and actual tool availability govern execution; instruction profiles cannot supply isolation. If delegation is unavailable, do useful authorized work directly, disclose self-review and leave a mandatory independent gate incomplete.

## Continuous improvement for every role

Use a proportionate PDSA cycle for each role: plan the contextual task and checks, execute through the owning skills, study observed results, and make authorized corrections with affected rechecks. Include this contract in every role packet, even for standalone work. Read the project-installed `docs/agents/continuous-improvement.md` (or approved equivalent) and relevant lessons; when absent, use this short cycle and report the setup gap. Bound repeated corrections to two attempts for the same failure, stopping sooner without progress; preserve read-only boundaries and route fixes to their authorized owner.

Collect outcome, checks/gaps, PDSA summary and useful lesson candidates (context, evidence/snapshot, cause confidence, correction/result, proposed prevention, limits and next check). `No new lesson identified` is valid. The orchestrator alone serializes and deduplicates writes to `docs/agents/lessons-learned.md` or the existing approved record, preserves previous entries, distinguishes hypotheses from validated local results and rereads saved entries before reporting persistence. Write every persisted lesson entry in English, including its title and all fields, even when project specifications or conversations use another language. Translate and summarize relevant observations into English; retain technical identifiers and source quotes only when needed, with an English explanation. This applies to the project's lessons record in `docs/` or its approved equivalent and keeps lessons reusable for improving the PentaPRO skills. Without a recording owner or write access, return the candidates and mark persistence pending. For isolated agent calls, the invoking main session is the orchestrator; direct main-agent selection must separate role execution from recording. Late lessons can remain local for the next authorized commit; do not create additional publication merely to include them. Reusable instruction changes require their own authority and evaluation.
