# Journey and equivalence evidence

For a port, replacement or reproduction, inventory the reference and intended scope before implementation: entry points, users and developer workflows, input acquisition/preparation, supporting utilities, startup/configuration, data locations, output/presentation and recovery. Classify each relevant capability preserve, adapt or exclude; cite the source, rationale, impact and authority. Resolve exclusions that conflict with the original objective before coding. Separate installed, repository development, automated and other material contexts.

In existing PRODUCT and PROOF records, link each stable requirement ID to scenario locators, responsible owner, observable acceptance and check. For shared behavior, identify every affected consumer, shared rule, intentional platform adaptation, exclusion and its consequence. Validate affected consumers without imposing unrelated platforms. Define readability by relevant grouping, labels, units, alignment, ordering, density and task questions. Sample normal, dense, error and constrained views where material; equivalence means the promised behavior and experience, not identical source or widgets.

Choose an early vertical slice that obtains or prepares input, launches, performs a representative task, makes the result understandable and recovers from a relevant failure. Match actual inputs and contexts when comparing a reference. Distinguish source inspection, rendered output and completed user task; each supports different claims. Record actual snapshot, environment, coverage and omissions. User feedback is a scoped observation, not proof of universal satisfaction. A partial comparison cannot prove complete equivalence.
