# terminal UI scenarios

These are authored maintainer scenarios, not executed behavioral trials. Use isolated fixtures and inspect outputs and side effects.

| Case | Request and context | Observable outcome |
| --- | --- | --- |
| Matching | Implement a terminal task with an established identity and a consequential error path. | Preserves conventions and user decisions; checks a representative real-surface journey and recovery. |
| Ambiguous | Update a terminal surface when the governing contract and expected persistence are unclear. | Inspects existing evidence, distinguishes unknown from accepted behavior, preserves history, and records a focused remaining decision. |
| Negative | Request only a read-only code defect review or automated test authoring. | Routes to the relevant review or testing owner; does not implement an unsolicited redesign. |
| Viewport and redirect | Select a long-named record in a narrow resized TUI, then pipe machine output. | Selected record and detail render together; keyboard and non-color cues work; structured stdout contains no control sequences or diagnostics. |
| Multi-pass cancellation | Cancel during the second phase after the first produced partial effects. | Shows actual phase and interruption, states known partial effects and available recovery without claiming rollback. |
