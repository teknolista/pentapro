# Native change specification

The project-root `pentapro/changes/` holds one directory per active change. Choose a unique descriptive name of two or three lowercase words separated by hyphens. Inspect active names and existing archives before creating a directory; never overwrite another change or treat a partial directory as an empty template. Use the [six change templates](../assets/change) as authoring guidance, creating `change.md`, `product.md`, `project.md`, `production.md`, `proof.md` and `process.md` in the selected active directory. Create no tool-specific metadata, schema or command dependency. The main session coordinates the lifecycle and delegates where supported; the specification owner writes content and reconciles the baseline.

## Author and review

1. Establish the project root, baseline revision and authoritative facts. Greenfield initialization supplies Pending root scaffolds, not accepted requirements. Brownfield work identifies prior requirements, affected IDs, actual behavior, compatibility and consumers. Investigate incomplete/conflicting evidence before claiming a baseline. Inspect other active changes for overlapping IDs or paths; coordinate ordering and recheck after another change lands.
2. Capture motivation, expected outcome, exclusions, impacted IDs and baseline in `change.md`; keep lifecycle state and artifact index there. Write supported facts and pending decisions in the other five files. Each pillar is present: if unchanged, explain why and link its actual baseline record rather than inventing content. Preserve the source and status of facts and identify unknowns and decision owners.
3. For each material behavior, record stable requirement and scenario IDs and observable before/after conditions. State whether it is added, modified, removed or renamed. For an existing requirement, reference the complete prior requirement and its scenarios; preserve all unaffected ones. Explain retirement, migration and recovery. Renaming an ID does not by itself require renaming code symbols. Record constraints/decisions in PROJECT, rollout and recovery in PRODUCTION, traceable checks and actual revision-bound outcomes in PROOF, and owners, numbered tasks, checks and handoff in PROCESS. Link facts rather than copying entire baseline records or duplicate task lists.
4. Obtain a separate specification review against the full governing records before dependent implementation; address consequential findings. A specification-only request ends after its requested deliverable. Implementation continues when requested and authorized; evidence and product acceptance remain distinct. On an interrupted session, inspect actual files, snapshot and recorded next action before continuing. Never treat file existence alone as a successful review.

## Reconcile after result acceptance

One explicit developer approval of the verified result normally authorizes consolidation, archive, commit and normal push; explicit narrower or separately requested gates prevail. A timeout, agent verdict or successful check does not constitute developer approval. The change itself owns proposed requirements until approval. Once approved, update affected baseline pillars with penta-pro and check every intended addition, modification, removal and rename against the recorded old text and scenarios. Preserve unrelated requirements and scenarios, stable identities, decisions and historical evidence. Record superseded or retired identities and migration impacts. Check task and evidence status against the final source snapshot, and mark stale evidence pending rather than relabeling it.

Before any multi-file reconciliation, record its scope, source revision, owner and pending files in PROCESS; serialize overlapping changes, inspect changes made since review, and stop if concurrent modification or a contract conflict cannot be reconciled safely. After writes, inspect resulting records and relative links, including those from `pentapro/changes/archive/YYYY-MM-DD_<name>/`; preserve provenance and refer to the actual archive path. Mark a partial write incomplete, record recovery and resume from current contents; never claim consistency solely from a successful move.

The factory owns lifecycle and archive. A completed change is archived only after accepted content and verification are reconciled; archive destination collisions do not overwrite. A cancelled change stays explicitly cancelled with any partial implementation, baseline impact, residual work and recovery decision recorded. Do not promote abandoned requirements as implemented or undo code without authority. Where retained code changes actual baseline behavior, identify the conflict and obtain a decision before updating baseline facts.

Reference documents are instructions to be tailored, not proof of correctness. Report scoped checks, executed evidence and remaining gaps; the presence of a change or its acceptance never proves deployment or universal software quality.
