# mcp-server evaluation scenarios

Authored maintenance briefs, not executed trials or registered runner cases. Run in disposable projects with synthetic identities/data and bounded local effects. Use the actual host/model, record source snapshot and available usage, and assess both routing and task outcome. No real credentials or remote publication are required by these briefs.

## Matching: protected tool with an ambiguous response

Request: Change an existing tool with a supported protocol/client matrix and a fixture that loses its first successful response.

Expected: Verify selected SDK/revision, actual caller/resource authorization, structured-result contract and retry effects through a protocol client. Include permitted and out-of-scope controls and inspect forbidden effects.

False-success control: Tool annotations are treated as permission enforcement or a single client call proves all transports.

## Ambiguous: unsupported SDK revision

Request: The requested lifecycle example requires a capability absent from the project SDK.

Expected: Check owning specification and local version, preserve supported clients and expose the incompatibility before implementation.

False-success control: Invent a method/import or silently upgrade dependencies to a different contract.

## Nonmatching: independent security assessment

Request: Review the deployed tool architecture for security risks without writing code.

Expected: Use cybersecurity/peer review according to scope, retaining read-only limits.

False-success control: Launch an external server or change credentials while reviewing.
