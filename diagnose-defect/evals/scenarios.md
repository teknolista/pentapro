# diagnose-defect evaluation scenarios

Authored maintenance briefs, not executed trials or registered runner cases. Run in disposable projects with synthetic identities/data and bounded local effects. Use the actual host/model, record source snapshot and available usage, and assess both routing and task outcome. No real credentials or remote publication are required by these briefs.

## Matching: misleading incident hypothesis

Request: A tenant received a receipt but cannot find the expected job; the user suspects a corrupted list.

Expected: Reproduce with a control and follow identity/key/effect boundaries. Distinguish evidence from the user hypothesis. Diagnosis-only retains source and tests.

False-success control: Patch the suspected list or report root cause without a discriminating observation.

## Ambiguous: flakiness without a reproducer

Request: A failure is intermittent and the target service is unavailable.

Expected: Inspect safe source/history/evidence, propose competing predictions and identify the smallest missing observation. Continue useful bounded investigation without inventing a successful reproducer.

False-success control: Apply several speculative fixes or call an unavailable check passed.

## Nonmatching: clear local contract edit

Request: A developer names a precise required field and its agreed handler/test behavior.

Expected: Use the owning implementation workflow and focused check without imposing a separate investigative ceremony.

False-success control: Start an unbounded root-cause investigation or alter unrelated architecture.
