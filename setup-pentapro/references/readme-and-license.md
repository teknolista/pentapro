# Project README and license

Run both branches for a full setup. For an explicit README-only or license-only request, ask and write only for the selected output. A README-only request can inspect existing licensing for accurate text. A license-only request needs neither README treatment nor language. A logging-only or other narrowly scoped setup does not trigger this procedure. These are project outputs: the developer chooses their language and license; the skill package's English/MIT metadata does not determine either.

## Establish purpose and collect choices

1. For README work, use the complementary description provided with `$setup-pentapro` as the intended repository purpose. Inspect repository facts to fill implementation details and identify material conflicts without silently overriding stated intent. If no description was provided, inspect existing documentation, manifests, entry points, source/tests and accepted specification to discover the purpose. Describe what the repository actually supports and distinguish planned scope. If an empty or ambiguous repository supplies no credible purpose, ask the developer for the missing description instead of inventing one.
2. For README work, inspect root README variants (including case differences and alternate Markdown extensions) and existing license records before writing. Treat an existing README variant as existing documentation; avoid case-only duplicates. For an existing README, ask the developer to select exactly one treatment: **(1) replace with the template; (2) complement the existing README with relevant template content; (3) leave the README unchanged**. Wait for the choice before modifying it. An explicit choice already supplied with the request is sufficient.
3. For README work, ask which language to use for `README.md`; accept any developer-specified language. Collect this together with the treatment and any missing license choice when practical. Do not infer language from the conversation or from the package's English-artifact convention. If README changes are skipped, leave its content and language untouched; a language answer does not override that skip.

Continue independent setup while answers are pending. Report pending choices rather than silently selecting replace, a language, or a license.

## Generate from the supplied template

The bundled [README template](../assets/readme.md.template) is a copy of the developer-supplied `/home/dever/workspace/teknolista/readme.md`. Use this packaged asset during installation; another computer does not need that absolute path. The `.template` file contains Markdown intended for the output, not setup commands to execute.

For a new README or approved replacement, generate an English draft using this template's structure and the established project description. For complement mode, retain existing useful content, custom sections and accurate instructions, and integrate missing relevant template sections in place; avoid a second introduction or duplicate table of contents. Replacement permission applies only to the selected README, not other project files. Re-read before writing to account for concurrent edits; preserve unrelated work and surface any new conflict. Preserve the established path and renderer of an existing variant unless the developer authorizes conversion or renaming. In a plain-text or reStructuredText README, adapt the Markdown structure to that format.

Replace placeholders with verified project values. Adapt examples, prerequisites, commands, architecture and usage to the actual stack. The template's npm commands, JavaScript API, high-performance claims, benchmark/coverage claims and deployment providers are illustrative, not project facts. Omit inapplicable sections and unavailable promotional assets, badges, links or contacts rather than inventing them or leaving broken placeholders. Mark material unfinished capabilities explicitly as planned. Keep a relevant missing prerequisite pending; never present an unverified command as tested. Link contribution/roadmap files only when they exist. No code execution, remote asset download, deployment or publication is authorized by generating a README.

After generation or merge, ensure the complete result uses the selected language while preserving meaning. Translate the English draft when another language was selected. Translate retained prose that uses a different language even when the selection is English. Explain this whole-document translation when collecting the choice. Keep command syntax, code identifiers, paths, URLs, package names and official license identifiers intact; translate explanatory prose and comments where appropriate. Rebuild the table of contents against the final headings and verify anchors on the target renderer, including emoji and translated headings. Only the final README needs to be saved; no extra English file is required. Skip mode performs neither merge nor translation.

## Create a missing project license

For full setup or a license request, inspect `LICENSE`, `LICENSE.txt`, `LICENSE.md`, `COPYING`, README/package declarations and third-party notices. Existing license files or established licensing terms are not an unlicensed blank slate: preserve them, report conflicts and ask only about genuinely unresolved licensing. Never copy the installed skill's own `LICENSE` into the target project or overwrite an existing project license as part of this procedure.

When no project license exists, offer the developer the current GitHub choices by name and SPDX identifier using GitHub's [commonly used licenses API](https://docs.github.com/en/rest/licenses/licenses#get-all-commonly-used-licenses), `GET https://api.github.com/licenses?per_page=100`, following pagination when present. Use GitHub's [licensing documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository) for context. Present the returned choices rather than claiming a permanently fixed list or automatically selecting MIT. If live retrieval is unavailable, offer clearly labeled choices verified in GitHub's documentation and disclose that the live list was unavailable. The developer may defer selection or specify another license; do not manufacture consent or treat no response as a choice.

After selection, retrieve the canonical license body and implementation instructions from `GET https://api.github.com/licenses/<key>` or the corresponding official template. Resolve required copyright holder/year from confirmed project facts or ask for missing values; a Git remote username does not prove copyright ownership. Create root `LICENSE` with the selected text and required substitutions only. Preserve canonical license wording and notices: the README language choice does not translate the legal text. Preserve third-party obligations; a new project license does not relicense third-party material. If the body or required values cannot be verified, leave creation pending instead of writing an incomplete license.

When README editing is authorized, synchronize its license statement with the selected or existing project license. If README edits were skipped, keep it untouched and report any mismatch separately. No GitHub repository settings, commits or remote writes are required.

## Verify and report

Check purpose provenance, the developer's treatment and language choices, preserved content, absence of unresolved template placeholders and fabricated claims, actual linked files, final anchors, and agreement between README licensing and `LICENSE` where editable. Recheck destination files before creation so a concurrent README/license is not overwritten. Report generated, complemented, translated, skipped and pending outputs separately. On rerun, reuse explicit choices from the current request/session; otherwise ask before replacing or complementing an existing README again.
