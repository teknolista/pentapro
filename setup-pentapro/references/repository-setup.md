# Full repository setup

This procedure adapts the tracker, triage and domain setup in Matt Pocock's `setup-matt-pocock-skills` to the teknolista collection and its PentaPRO records. Scope it to the actual request. Do not silently replace a project's chosen tracker, domain documents, specifications or instruction hierarchy.

## Explore and select

- Identify the current project root, `git remote -v`, existing root `AGENTS.md` and `CLAUDE.md`, `.gitignore`, `docs/agents/`, existing `pentapro/`, README, manifests, CI and verified build/test commands. Read existing applicable instructions before edits. Check the Git index for tracked or staged `AGENTS.log` and `AGENTS.log.*` before any prompt append; a pattern cannot untrack a file. Do not read old prompts for discovery.
- Inspect existing `GLOSSARY.md`, `GLOSSARY-MAP.md`, legacy `CONTEXT.md` / `CONTEXT-MAP.md`, existing decision records and `docs/adr/` without moving or deleting them. Check `.scratch/` and available tracker integrations. Detect whether an applicable `triage` skill is installed, and monorepo or bounded-context signals.
- Reuse an existing tracker and domain layout; derive a sensible default from an existing GitHub or GitLab remote or `.scratch/` where reliable. Otherwise ask the user which tracker is authoritative. The options include GitHub, GitLab, local Markdown, and a user-described alternative. A remote's existence alone does not prove a tracker is used or reachable: mark unverified facts, do not silently configure a remote, and record inaccessible prerequisites. GitHub/GitLab CLI checks are read-only but may require access; preserve the actual result.
- Choose a single PentaPRO domain context unless established boundaries or the user require a context map. Keep existing glossary and ADR conventions as authoritative until a migration is explicitly authorized. If migration is requested, inventory exact files, conflicts and references, preserve decision IDs and source history, and verify inbound links. Use the project's existing layout where established; do not create duplicate competing records.

## Write setup records

- Use [GitHub](../assets/issue-tracker-github.md), [GitLab](../assets/issue-tracker-gitlab.md), or [local tracker](../assets/issue-tracker-local.md) templates for `docs/agents/issue-tracker.md`; adapt paths and operations to verified project conventions. For another tracker, write its actual workflow. Treat PRs as a request surface only if established or explicitly requested. Record no credentials. These files describe possible operations, not authorization to create issues or send messages.
- If triage is installed and relevant, configure `docs/agents/triage-labels.md` from [the mapping](../assets/triage-labels.md), keeping existing label names and asking when the mapping cannot be inferred. The upstream default roles are `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, and `wontfix`. Do not add a triage section when the skill is absent. Creating remote labels is a separate external mutation; perform it only with actual authority. Report uncreated labels rather than claiming they exist.
- Adapt [domain guidance](../assets/domain.md) to the project's chosen sources in `docs/agents/domain.md`. In a new PentaPRO project the default glossary is `pentapro/product/domain.md` and decisions live in `pentapro/project/decisions.md`; multi-context projects can use a map and per-context records. Do not state that legacy documents have been migrated when they have not.
- In root `AGENTS.md`, merge a single `## Agent skills` block that points to records actually created, conditionally including triage. Preserve unrelated sections. For a new file or when broader guidance was requested, adapt relevant sections of [the project instruction template](../assets/agents.md); use confirmed facts, mark meaningful unknowns and omit irrelevant rows. Never replace user-authored guidance with generic template material. If `CLAUDE.md` exists, preserve it; add an `@AGENTS.md` import only when appropriate for that host and within scope, without duplicating it. Do not create `CLAUDE.md` by default.
- The inline logging rule in `SKILL.md` is the source for the complete `AGENTS.md` section; the template contains the same rule. Ensure `.gitignore` excludes `AGENTS.log` and `AGENTS.log.*`. If the log is already tracked or staged, stop before capture and report the privacy conflict; do not remove it from the index without authority. Avoid exposing prior prompts. Log-file redaction and agent compliance are best effort; no hook is installed by this procedure.

## Project facts and PentaPRO handoff

Classify evidence by ownership: users, scope and terminology in PRODUCT; architecture, dependencies and decisions in PROJECT; environments and operations in PRODUCTION; checks and evidence in PROOF; workflow and authority in PROCESS. Keep runtime commands that every agent needs in project guidance and link to canonical details. Preserve IDs and prior decisions; mark inference proposed and missing facts pending. Never store secrets.

If a full setup includes specification initialization, use the installed `penta-pro` skill's actual initializer and workflow; inspect the target first and do not overwrite a specification. Do not force PentaPRO upon a project with another accepted governing specification. If the initializer or skill is unavailable, report the gap and place relevant setup facts and provenance in `docs/agents/setup-notes.md` when a durable handoff is needed. An accepted setup or specification does not grant authority to implement, publish, archive, or deploy.

If initialization fails, preserve any partial output and report the failure. Do not manufacture missing pillar files as a substitute or treat partial output as a complete specification. Continue independent setup steps and retain requested facts with their sources, dates and confirmed, proposed or pending status in `docs/agents/setup-notes.md`; reconcile them through `penta-pro` when the specification is available. Keep existing IDs and decisions intact.

## Completion and repeatability

Check `AGENTS.md`, ignore rules, chosen tracker and domain files, any triage mapping, and local links. Verify actual writes and report what was not configured. On a rerun, preserve user edits and existing choices, update only affected blocks, and do not duplicate sections or tracker files. Report follow-up for unresolved choices and recommend `$penta-pro` when a specification is requested or appropriate; the user can edit setup records directly later.
