# Project-local factory setup

Run this procedure for a full setup unless the user requested a narrower scope. Work only in the target project. Inspect existing `.codex/`, `.agents/skills/`, `pentapro/`, root instructions and tracked/untracked work first. Preserve existing project decisions, configuration and local edits. Do not change user, global or system configuration. The main session is the orchestrator; its run contract is owned by the installed `software-factory` skill.

## Native change structure

Inspect the target repository and existing `pentapro/` records first. For full setup or an explicitly requested native factory setup, prepare `pentapro/changes/archive/` under the project root and concise directory guidance. Keep all five existing specification dimensions and established project records. Use the installed `penta-pro` initializer when available after inspecting its effects; it creates missing Pending scaffolds and refuses unsafe changes/archive symlinks. If unavailable, inspect each path and parent before creating only the missing directories, never follow symlinks or overwrite content, and report that scaffold checks were unavailable. A setup rerun preserves active changes, archives, existing indexes, logs and custom instructions. Do not create a fictional active change, populate project facts or mark a baseline accepted. A narrower logging-only request does not create these paths.

The main session is the exploration/orchestration agent. It gathers intent, preserves a baseline, creates a uniquely named active change only for an authorized development request and directs the applicable specialist roles through specification, implementation and independent verification. `penta-pro` owns the five-dimensional specification, `software-delivery` owns implementation planning and `software-factory` owns the change lifecycle and handoffs. No separate SDD utility or configurable schema is required.

After review, one explicit developer approval of the concrete result authorizes baseline consolidation, archive, commit and normal push by default. Preserve a developer's explicit narrower scope or request for separate approval steps, and obey host permissions and delivery stop conditions. Cancelled work never promotes abandoned intent; record retained effects and recovery decisions before archive.

## Host roles

Identify the actual target host from the session or an explicit user choice; installed directories alone do not identify the active host. If uncertain, ask which host to configure and continue independent setup. For each of the six [role bundles](../assets/agents/), copy the selected host template to its project-local destination:

| Host | Template | Destination for `factory-<role>` |
| --- | --- | --- |
| Codex | `codex.toml` | `.codex/agents/factory-<role>.toml` |
| Claude Code | `claude-code.md` | `.claude/agents/factory-<role>.md` |
| Cursor | `cursor.md` | `.cursor/agents/factory-<role>.md` |
| GitHub Copilot | `github-copilot.md` | `.github/agents/factory-<role>.agent.md` |
| OpenCode | `opencode.md` | `.opencode/agents/factory-<role>.md` |
| Antigravity | `antigravity.md` | `.agents/agents/factory-<role>.md` |

Role names in workflow packets are logical names such as `factory_shipper`. Resolve them to the discovered host ID before invocation: Codex, Claude Code and Antigravity use the template's `name`; Cursor uses the hyphenated `name` (`factory-shipper`), OpenCode uses the destination filename stem (`factory-shipper`), and Copilot uses the profile's discovered identity/display name. Record the mapping in project guidance and delegation packets, and confirm discovery rather than assuming underscore and hyphen aliases are interchangeable. Existing custom names take precedence.

Inspect every destination and create missing files only; preserve customized files, previous Codex roles and settings. Do not change user/global configuration or permissions. Check host version, skill discovery and the supported model and effort selection for that particular client. Codex templates retain their selected model settings; other hosts inherit their available session model rather than inventing cross-provider IDs. Preserve the selected role model and effort as cost-conscious defaults. Developers may change project-local settings; respect their choices and do not silently substitute a model. For hosts without role-level fields, preserve their existing model selection and report the limitation; do not invent unsupported metadata. Configuration alone does not establish runtime selection, so report what the host actually exposes without blocking solely because runtime metadata is unavailable.

Check destination syntax and names, required read/command/edit capabilities and access to installed skills, then verify actual host discovery and a bounded invocation where supported and authorized. Report separately installed files, discovery, runtime model/effort evidence, and untested or unsupported capabilities. Files alone do not prove invocation, isolation or model use. Cursor also discovers `.claude/agents/` and `.codex/agents/`; its `.cursor/agents/` definitions take precedence when identities conflict. Inspect existing names and effective discovery before installing to avoid duplicate or shadowed roles. Cursor read-only permissions can block required prompt logging; these templates express role boundaries in instructions and do not set `readonly`. Check the host permissions separately. Do not enable delegation, network, or weaken sandbox/approvals to make a role work. Preserve existing host choices and report conflicts. See [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Claude Code](https://code.claude.com/docs/en/sub-agents), [Cursor](https://cursor.com/docs/subagents), [Copilot](https://docs.github.com/en/copilot/reference/custom-agents-configuration), [OpenCode](https://opencode.ai/docs/agents/) and [Antigravity](https://antigravity.google/docs/subagents).

## Continuous improvement setup

For full setup or explicitly requested factory-agent setup, create missing `docs/agents/continuous-improvement.md` from the bundled [PDSA protocol](../assets/continuous-improvement.md) and `docs/agents/lessons-learned.md` from the [empty lessons template](../assets/lessons-learned.md). Reuse an existing approved equivalent rather than creating a competing record; resolve and communicate its path in role packets and project guidance. Preserve populated records, custom protocols, original lesson IDs and status on reruns. Report conflicts and partial installation honestly; never reset a record to the empty template. A logging-only setup creates neither file.

In project host guidance, explain that directly invoking a factory role without further detail requests its defined workflow in the current project and session. The orchestrator preserves that intent, the configured model and effort, developer customizations, applicable permissions and role-specific stop conditions. A direct shipper invocation requests git-ship review, commit and normal push; completed implementation alone does not.

Merge one concise `Factory continuous improvement` section into the project's active host instructions (root `AGENTS.md` where supported, or the existing host instruction entrypoint). State that all six roles use PDSA, consult relevant existing lessons, and return evidence-backed candidates; only the orchestrator writes the lessons record, always in English regardless of the project specification language. A standalone role's invoking main session is the orchestrator; direct main-agent selection separates role work from subsequent orchestrator recording. Point to the actual protocol and record. Preserve surrounding guidance and avoid duplicate sections on reruns. Installing files does not prove a host reads them: verify its instruction entrypoint or report unavailable discovery. Late lessons may remain local until a subsequent authorized commit.

Verify both documents, instruction pointers, all six role handoffs, preserved read-only boundaries and standalone behavior. Report any missing orchestrator or write capability as persistence pending, without claiming the lesson was saved. No hook, scheduler, global memory or automatic skill rewriting is installed.

## Execution record setup

For full setup or explicitly requested factory-agent setup, create missing `docs/agents/runs/README.md` from the bundled [directory guide](../assets/runs-readme.md). Reuse an approved equivalent and communicate its path; preserve existing records and custom instructions. Setup prepares this directory only and does not create a run, install a scheduler or copy a competing workflow engine. Logging-only setup leaves it untouched.

Explain in host guidance that substantial factory/multi-agent runs need a durable record, only the orchestrator writes it, and role packets carry run ID/path/version/input fingerprint. The installed software-factory companion owns `references/run-records.md` and `scripts/run_state.py`; resolve its actual path and Python/Git prerequisites. Report missing capabilities and use an approved equivalent rather than claiming automatic validation. The record and English lessons are separate artifacts. Verify the directory guide, owner, path and preservation on rerun; existing projects adopt the new guidance through reviewed reconciliation, not template replacement.

## Handoff and verification

Check that `software-factory`, `penta-pro`, `software-delivery`, `peer-review` and `git-ship` are available in the project. Install missing packages at project scope only when a verified source and version are available; otherwise report the gap. Point project instructions to the installed `software-factory` skill, native change workflow and project role names without duplicating their procedures. For a new product use PentaPRO when specification is requested. Implementation, Git operations, archive, deployment and external changes follow the actual request and policy. Verify TOML parsing, role names and instructions, project scope, preserved existing files, native change/archive structure, installed skills and all incomplete prerequisites. Repeating setup must not overwrite customized agents or create duplicate sections. Report a concrete first prompt and the status of each capability; do not call setup a successful end-to-end factory trial.

## Plugin-installed resources

PentaPRO plugin installation distributes the same skill packages and agent templates; it does not instantiate global agents. Resolve installed skill IDs/paths from the host registry, including namespaces. Keep the target checkout separate from read-only plugin/cache paths, use project-local agent destinations and preserve custom records on rerun or plugin update. A shared plugin update never authorizes replacing customized project agents. Resolve existing copies before installing another package source, and report missing host/model capability honestly.
