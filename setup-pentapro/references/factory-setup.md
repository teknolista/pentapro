# Project-local factory setup

Run this procedure for a full setup unless the user requested a narrower scope. Work only in the target project. Inspect existing `.codex/`, `.agents/skills/`, `openspec/`, root instructions and tracked/untracked work first. Preserve existing project decisions, configuration and local edits. Do not change user, global or system configuration. The main session is the orchestrator; its run contract is owned by the installed `software-factory` skill.

## OpenSpec

Check `openspec --version` and `openspec init --help` before initialization. Verify the installed CLI's documented behavior for project-scoped skills and tool integration; do not assume flags or defaults across versions. If `--scope project` is supported, select it explicitly together with the actual host, for example `openspec init --scope project --tools codex` when supported. Inspect affected paths and legacy migration behavior before running any initializer: a non-interactive invocation may remove legacy marker blocks. Preserve modified files and existing configuration; do not use `--force` to bypass conflicts. If safe project-only behavior cannot be established, do not run the command; report the missing prerequisite and continue other setup. Installing or updating a CLI is limited to project scope and requires a verified package and version. Report network or permission failures.

Validate the selected schema, `openspec/config.yaml`, generated project-local skills and the CLI's actual status/validation commands. Keep project facts concise; don't invent product requirements. Reuse an existing OpenSpec setup and preserve its schema and customized skills. An initializer can create the root and then fail to install host skills, for example if the upstream download is unavailable. Inspect both outputs before claiming success or retrying. Complete the missing install only when the installed CLI supports a project-local retry that preserves existing files. Project-local installation may require network access. Follow the project's dependency and ignore conventions; avoid accidentally staging `node_modules/` or caches, and preserve the appropriate manifest and lockfile when the project uses them. Record the actual CLI version, tools, scope and remaining gap. Use the installed version's documentation, including [OpenSpec project setup](https://openspec.dev/docs/setup).

## Host roles

Identify the actual target host from the session or an explicit user choice; installed directories alone do not identify the active host. If uncertain, ask which host to configure and continue independent setup. For each of the six [role bundles](../assets/agents/), copy the selected host template to its project-local destination:

| Host | Template | Destination for `factory-<role>` |
| --- | --- | --- |
| Codex | `codex.toml` | `.codex/agents/factory-<role>.toml` |
| Claude Code | `claude-code.md` | `.claude/agents/factory-<role>.md` |
| GitHub Copilot | `github-copilot.md` | `.github/agents/factory-<role>.agent.md` |
| OpenCode | `opencode.md` | `.opencode/agents/factory-<role>.md` |
| Antigravity | `antigravity.md` | `.agents/agents/factory-<role>.md` |

Role names in workflow packets are logical names such as `factory_shipper`. Resolve them to the discovered host ID before invocation: Codex, Claude Code and Antigravity use the template's `name`; OpenCode uses the destination filename stem (`factory-shipper`), and Copilot uses the profile's discovered identity/display name. Record the mapping in project guidance and delegation packets, and confirm discovery rather than assuming underscore and hyphen aliases are interchangeable. Existing custom names take precedence.

Inspect every destination and create missing files only; preserve customized files, previous Codex roles and settings. Do not change user/global configuration or permissions. Check host version, skill discovery and the supported model and effort selection for that particular client. Codex templates retain their selected model settings; other hosts inherit their available session model rather than inventing cross-provider IDs. The shipper requires actual `gpt-6-luna` and `high`: install its template but report it blocked until the host can select and verify both. Do not replace it with a different model or pretend a configured value proves runtime selection. This limitation may prevent shipping on a host that cannot provide Luna/high; the developer may perform separately authorized shipping using git-ship in a compatible environment.

Check destination syntax and names, required read/command/edit capabilities and access to installed skills, then verify actual host discovery and a bounded invocation where supported and authorized. Report separately installed files, discovery, runtime model/effort evidence, and untested or unsupported capabilities. Files alone do not prove invocation, isolation or model use. Do not enable delegation, network, or weaken sandbox/approvals to make a role work. Preserve existing host choices and report conflicts. See [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Claude Code](https://code.claude.com/docs/en/sub-agents), [Copilot](https://docs.github.com/en/copilot/reference/custom-agents-configuration), [OpenCode](https://opencode.ai/docs/agents/) and [Antigravity](https://antigravity.google/docs/subagents).

## Continuous improvement setup

For full setup or explicitly requested factory-agent setup, create missing `docs/agents/continuous-improvement.md` from the bundled [PDSA protocol](../assets/continuous-improvement.md) and `docs/agents/lessons-learned.md` from the [empty lessons template](../assets/lessons-learned.md). Reuse an existing approved equivalent rather than creating a competing record; resolve and communicate its path in role packets and project guidance. Preserve populated records, custom protocols, original lesson IDs and status on reruns. Report conflicts and partial installation honestly; never reset a record to the empty template. A logging-only setup creates neither file.

Merge one concise `Factory continuous improvement` section into the project's active host instructions (root `AGENTS.md` where supported, or the existing host instruction entrypoint). State that all six roles use PDSA, consult relevant existing lessons, and return evidence-backed candidates; only the orchestrator writes the lessons record, always in English regardless of the project specification language. A standalone role's invoking main session is the orchestrator; direct main-agent selection separates role work from subsequent orchestrator recording. Point to the actual protocol and record. Preserve surrounding guidance and avoid duplicate sections on reruns. Installing files does not prove a host reads them: verify its instruction entrypoint or report unavailable discovery. Late lessons may remain local until a subsequent authorized commit.

Verify both documents, instruction pointers, all six role handoffs, preserved read-only boundaries and standalone behavior. Report any missing orchestrator or write capability as persistence pending, without claiming the lesson was saved. No hook, scheduler, global memory or automatic skill rewriting is installed.

## Execution record setup

For full setup or explicitly requested factory-agent setup, create missing `docs/agents/runs/README.md` from the bundled [directory guide](../assets/runs-readme.md). Reuse an approved equivalent and communicate its path; preserve existing records and custom instructions. Setup prepares this directory only and does not create a run, install a scheduler or copy a competing workflow engine. Logging-only setup leaves it untouched.

Explain in host guidance that substantial factory/multi-agent runs need a durable record, only the orchestrator writes it, and role packets carry run ID/path/version/input fingerprint. The installed software-factory companion owns `references/run-records.md` and `scripts/run_state.py`; resolve its actual path and Python/Git prerequisites. Report missing capabilities and use an approved equivalent rather than claiming automatic validation. The record and English lessons are separate artifacts. Verify the directory guide, owner, path and preservation on rerun; existing projects adopt the new guidance through reviewed reconciliation, not template replacement.

## Handoff and verification

Check that `software-factory`, `penta-pro`, `software-delivery`, `peer-review`, `git-ship` and applicable OpenSpec skills are available in the project. Install missing packages at project scope only when a verified source and version are available; otherwise report the gap. Point project instructions to the installed `software-factory` skill, OpenSpec workflow and project role names without duplicating their procedures. For a new product use PentaPRO when specification is requested. Implementation, Git operations, archive, deployment and external changes follow the actual request and policy. Verify TOML parsing, role names and instructions, project scope, preserved existing files, OpenSpec status, installed skills and all incomplete prerequisites. Repeating setup must not overwrite customized agents or create duplicate sections. Report a concrete first prompt and the status of each capability; do not call setup a successful end-to-end factory trial.

## Resolve a selected OpenSpec store

When the project or user selects a registered store, verify support in the installed CLI and resolve its identity with the documented read-only inspection commands before writing. On versions supporting them, use `openspec store list --json` and `openspec list --json --store <id>` to inspect the selected store and returned root. Carry `--store <id>` on subsequent commands that support it; an unscoped command may select a different local root. Resolve relevant symlinks and check the actual destination against authorized scope; an explicitly selected external store can be legitimate. Record the planning root separately from the implementation checkout.

Distinguish an uninitialized project from a declared store that is unavailable or invalid. Inspect structured errors as well as exit status. Never initialize a replacement root to work around an unresolved store. A setup request may authorize project initialization; an apply/verify request does not silently authorize setup elsewhere. Reuse one resolved identity in downstream change and factory records, rather than guessing paths from the current directory. Verify exact command and JSON support against the installed version. [OpenSpec store and project checks](https://github.com/Fission-AI/OpenSpec/blob/0c737dc1b543249b38b0f4716816fcf493d894dd/skills/openspec-apply-change/SKILL.md)

## Plugin-installed resources

PentaPRO plugin installation distributes the same skill packages and agent templates; it does not instantiate global agents. Resolve installed skill IDs/paths from the host registry, including namespaces. Keep the target checkout separate from read-only plugin/cache paths, use project-local agent destinations and preserve custom records on rerun or plugin update. A shared plugin update never authorizes replacing customized project agents. Resolve existing copies before installing another package source, and report missing host/model capability honestly.
