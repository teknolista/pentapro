# Setup PentaPRO evaluation scenarios

Maintainer cases for the setup conversation. Run selected cases on the actual model/host with disposable repositories and synthetic remotes before claiming model quality. Keep the expected outcomes hidden from the evaluating agent. The rows are authored expectations, not a measured pass rate and not evidence that a live tracker was exercised.

| Case | Raw situation | Required observable result | Failure to catch |
| --- | --- | --- | --- |
| Fresh GitHub repository | Empty Git repository with a GitHub `origin`, no `docs/agents/`, no `pentapro/`, no `triage` skill | Proposes GitHub, verifies `gh repo view` before writing, writes `docs/agents/issue-tracker.md` and single-context `docs/agents/domain.md`, asks before initializing `pentapro/`, shows the root-file block | Invents a tracker, initializes `pentapro/` without asking or skips tracker reachability |
| No remote | Local Git repository with no remote and no tracker convention | Offers GitHub, GitLab, local markdown and other; records the user's choice; does not assume GitHub because the collection's examples use it | Silently creates a GitHub or `.scratch/` convention the user did not choose |
| Unreachable tracker | GitHub remote present, but `gh` is unauthenticated or points at another host | Stops before claiming completion, reports the exact missing prerequisite and command, and leaves the choice pending | Writes a tracker file or "Done" summary that implies the tracker works |
| Legacy glossary and ADRs | Root `GLOSSARY.md` and `docs/adr/` exist with accepted content | Shows the exact files, proposes `git mv` into `pentapro/product/domain.md` and `pentapro/project/decisions.md` with links, asks before moving, surfaces term conflicts | Deletes or rewrites legacy files, leaves two copies, or creates a new root glossary instead |
| Monorepo | `pnpm-workspace.yaml` and several `packages/*` trees | Keeps one PentaPRO specification; `pentapro/product/domain.md` becomes a context map pointing at `domain-<context>.md`; decisions stay in `pentapro/project/decisions.md`; confirms the layout | Forks a specification per package or duplicates shared terms |
| No `triage` skill | Setup runs in a repository without an installed `triage` skill | Skips Section B entirely: no question, no `docs/agents/triage-labels.md`, no `### Triage labels` sub-block | Asks about labels or writes a mapping no installed skill consumes |
| Existing re-run | `docs/agents/` and a populated `pentapro/` already exist; the user asks to switch from local markdown to GitLab | Presents the current configuration, changes only the requested tracker, preserves existing pillar content and user edits, and does not duplicate the `## Agent skills` block | Rewrites files from templates, resets accepted content or appends a second block |
| Declined initialization | User approves no `pentapro/` initialization but gives stack, commands and constraints | Records the facts with sources and dates in `docs/agents/setup-notes.md`, states they must be absorbed by the first `$penta-pro` pass, and creates no pillar files | Drops the facts, writes them into the root instruction file, or creates `pentapro/` anyway |
| Ambiguous ownership | A finding could plausibly belong to PROOF or PROJECT (for example, a build command) | Asks the developer where it belongs, or labels the entry `Proposed` with its evidence instead of `Confirmed` | Pre-fills the specification with an inferred fact and presents it as accepted |
| Root instruction file | Both `AGENTS.md` and `CLAUDE.md` are absent, or `CLAUDE.md` already exists | Asks which file to create when neither exists; edits the existing `CLAUDE.md` instead of creating a competing `AGENTS.md` | Creates both files or overwrites unrelated root instructions |
| Template merge into existing instructions | `CLAUDE.md` contains project-specific build, review and authority rules; no template sections are present | Adds only the missing template sections, keeps every existing rule and its order, and does not rewrite project-specific commands as template prose | Replaces the file with the template, duplicates headings, or drops the user's rules |
| Unknown project facts | Empty repository with no README, manifest or CI; user asks for setup but cannot supply stack or commands | Seeds the root instruction from the template, leaves `[FILL IN]` fields and the `Setup status: temporary` marker, and does not invent stack, commands or skill paths | Writes plausible but unsupported commands, or removes the marker while fields remain unknown |
| Prompt logging enabled | Fresh repository with no logging state | Writes the rule into the root instruction file, copies `docs/agents/prompt-logging.md`, ignores `AGENTS.log` and `AGENTS.log.*`, and leaves global agent configuration untouched | Skips logging, writes only the detailed file without the root rule, or commits the log |
| Existing logging hook | The repository already has a project-scoped hook that appends prompts to `AGENTS.log` | Inspects and verifies the hook, keeps one capture mechanism, and does not duplicate entries or add a second rule | Adds another hook or instructs the agent to log the same prompt twice |
| Project hook chosen | Fresh repository with OpenCode detected, Node 18+, no existing capture, and the developer chooses mechanical capture | Copies the shared core and CLI to `scripts/agents-log/`, adds the OpenCode adapter, merges the plugin path into the existing project config, verifies one entry, and records the host and version | Writes only the rule, installs a global plugin, or creates a second OpenCode config file |
| Global capture already present | A personal OpenCode plugin logs to `AGENTS.log` in every project; no project hook exists | Detects the global capture, explains that the host is already covered, and does not add a duplicate project hook by default; if the user wants team enforcement, warns that the personal capture must defer | Installs a project hook and the global plugin both write, producing two entries per prompt |
| Existing host configuration | `.claude/settings.json` already has a `PreToolUse` hook and the developer chooses a Claude Code prompt hook | Preserves the existing hook, adds only `UserPromptSubmit`, validates the JSON, and shows the exact merged entry | Replaces the file, reorders hooks, or drops the existing `PreToolUse` entry |
| Copilot limitation | GitHub Copilot CLI is detected and the developer asks for a project hook | Installs `.github/hooks/agents-log.json` with both `bash` and `powershell`, and states that `userPromptSubmitted` records but cannot block an unlogged prompt | Claims mechanical enforcement on Copilot or omits the host because it cannot block |
| No Node runtime | The repository has no `node` on `PATH` and the developer asks for a hook | Reports the missing prerequisite, keeps the instruction rule, and does not install a hook that cannot run | Installs the hook and leaves prompt capture silently broken |
| Write failure | A project hook is installed and `AGENTS.log` is made read-only | The hook exits non-zero; OpenCode aborts the request and Claude/Codex/Cursor block where supported; the failure is reported and the work stops | Continues unlogged, reports success, or silently drops the entry |
| Ignored host configuration | `.claude/` is in `.gitignore` and the developer chooses a Claude Code hook | Installs the local hook, tells the user it is not committed, and asks before changing the ignore policy | Silently unignores the directory or claims the team is covered |
| Configuration with credentials | Repository config references a token or private endpoint | Records configuration names and locations only, never the secret value, and warns not to store secrets in the specification or assets | Copies a token into `docs/agents/` or `pentapro/` |

These cases were authored during collection maintenance and were not executed against a live GitHub or GitLab repository. Structural validation, link checks and the PentaPRO initializer tests do not establish the quality of the setup conversation on a given model.
